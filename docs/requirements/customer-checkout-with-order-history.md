## 1. Problem statement

The Shop Platform has no way for a customer to find products, build a cart, turn it into a paid order, or see what they previously bought. Without checkout the platform earns nothing; without order history customers cannot confirm or review purchases. This feature lets a customer register and sign in, browse a basic product catalogue, keep a cart, check out and pay by card through a payment provider's hosted page (test mode only, so card data never reaches our servers), and view their own order history and order details.

Because the repository is greenfield, no catalogue, cart, customer account or authentication capability exists. The Product Owner has decided that this feature delivers a minimal version of each (OQ-1, OQ-2).

## 3. Scope statement

- **In scope:**
  - Basic product catalogue: browse/list and view products; products are seeded, no admin UI.
  - Cart: add, remove, change quantity, view; persisted per customer and kept across sign-out/sign-in.
  - Basic customer accounts: register, sign in, sign out with email and password.
  - Checkout from the cart, order summary, hosted card payment (test mode), payment outcome handling (including late, failed and unknown outcomes), order confirmation.
  - Order history list and order detail.
  - Audit logging, and privacy and retention rules for order and account data.
- **UI in scope: YES.** The customer-facing web app (React) is in scope for catalogue, product, cart, registration, sign-in, checkout, confirmation, history and detail screens, so Phase 3 (UX spec, prototype, HG-2) applies.
- Out of scope: see section 9.

## 5. User stories and acceptance criteria

All ACs are Given/When/Then. Time targets are server-side or end-to-end as stated, measured in the CI/staging test environment. Money is USD displayed as `$1,234.56`.

### US-1 Start checkout (REQ-1, REQ-13, REQ-9, REQ-22)

As a customer, I want to start checkout from my cart so that I can pay for the items.

- **AC-1.1** Given I am signed in and my cart has at least one item, when I choose "Checkout", then I am shown the order summary, no order record exists yet, no payment has been started and no order is marked paid (the order is created at "Pay").
- **AC-1.2** Given I am signed in and my cart is empty, when I attempt to check out (via UI or API), then checkout is refused with a message stating the cart is empty (API: HTTP 4xx with the error model), and no order record is created.
- **AC-1.3** Given I am not signed in, when I attempt to start checkout (UI or API), then the API returns HTTP 401, no order is created, and the UI directs me to sign in; after I sign in, my cart is intact (see AC-11.6).
- **AC-1.4** Given my cart contains a line that is no longer purchasable (product flagged not purchasable) or whose price differs from the current catalogue price, when I start checkout, then no order is created and no payment is started, the message lists each affected item and the change, price-changed lines in the cart are updated to the current price, not-purchasable lines are flagged and must be removed by me, and I can return to the cart.
- **AC-1.5** Given I send a checkout request referencing a cart owned by another customer, when the API processes it, then it returns HTTP 404 and creates nothing.
- **AC-1.6** Given a checkout was rejected under AC-1.4 for price changes only, when I start checkout again without changing the cart, then the summary is shown at the new price and I can proceed to pay.
- **AC-1.7** Given a cart total of $0.49, $0.50, $999,999.99 and $1,000,000.00 (one cent below the minimum, the minimum, the maximum, one cent above the maximum), when I start checkout, then $0.50 and $999,999.99 proceed, and $0.49 and $1,000,000.00 are blocked with a message stating the allowed range, and no order is created.

### US-2 Review order summary (REQ-2, REQ-22)

As a customer, I want to see exactly what I will pay so that I can confirm before paying.

- **AC-2.1** Given I am at checkout, when the summary loads, then it lists every cart line with name, quantity, unit price and line total, plus the order total, all formatted as USD (`$1,234.56`).
- **AC-2.2** Given a summary is displayed, when I compare amounts, then the order total equals the sum of line totals (no tax, shipping or discounts), computed in integer cents, with zero rounding discrepancy in 100% of the automated test cases.
- **AC-2.3** Given I submit checkout with client-modified prices or totals, when the server processes it, then the stored order uses server-side prices and the tampered values are ignored (verified by an API test comparing stored total to catalogue prices).
- **AC-2.4** Given the summary cannot be loaded (server error), when the failure occurs, then an error message with a retry action is shown and the cart is unchanged.

### US-3 Pay by card via hosted payment (REQ-3, REQ-4, REQ-5, REQ-22, REQ-23, REQ-24)

As a customer, I want to pay by card on a secure page so that my card details stay protected.

- **AC-3.1** Given I confirm the summary, when I choose "Pay", then exactly one pending_payment order is created with its lines snapshotted from the cart, I am taken by full redirect to the provider's hosted payment page (or shown provider-hosted iframe fields), and the amount shown there equals the order total.
- **AC-3.2** Given I complete a payment in a recorded end-to-end run, when the HTTP traffic to our API and the application logs and database are inspected, then there are 0 occurrences of a PAN, CVV or expiry value, and no card input fields are rendered by our own page elements outside provider-hosted content.
- **AC-3.3** Given the application is configured with a non-test (live) provider credential, when the API starts, then it refuses to start and logs a configuration error without printing the credential. How a live credential is recognised (for example key prefix or provider mode flag) depends on the provider and is defined in Phase 4.
- **AC-3.4** Given I click "Pay" twice within 1 second, or refresh or navigate back and resubmit with an unchanged cart, when the requests are processed, then exactly 1 order and exactly 1 provider payment exist for that checkout attempt (customer plus cart version).
- **AC-3.5** Given the provider reports a successful payment, when the server verifies it with the provider, then the order status becomes "paid" and the paid amount equals the order total.
- **AC-3.6** Given the provider's confirmation callback is delivered more than once, when each delivery is processed, then the order is updated once and later deliveries return success without changing the order.
- **AC-3.7** Given a callback or return request that fails authenticity verification (invalid signature or unknown reference), when it is received, then it is rejected with HTTP 4xx, the order is unchanged, and an audit event is written. The callback endpoint is the only endpoint not requiring a customer session (REQ-9).
- **AC-3.8** Given I have the same unchanged cart open in two tabs, when I choose "Pay" in both, then exactly 1 pending order and exactly 1 provider payment exist and both tabs lead to the same payment session (an unchanged cart reuses the pending order).
- **AC-3.9** Given I have a pending order, when I go back, change the cart (add, remove or change a line) and choose "Checkout" then "Pay", then the old order is cancelled after the provider confirms its session is closed (or, if the provider reports it already paid, the old order becomes paid and the new checkout is refused with a message), a new order with the new lines is created, exactly 1 pending order exists, and at most 1 successful charge results.
- **AC-3.10** Given I edit my cart while my order is pending payment, when the original payment is then verified as successful, then the paid order contains the original snapshotted lines and total, and the cart changes made after "Pay" remain in my cart (see AC-4.6).
- **AC-3.11** Given two browser sessions of mine start checkout at the same moment with different cart versions, when both choose "Pay", then exactly 1 pending order remains active (the later supersedes the earlier under AC-3.9) and at most 1 successful charge results.
- **AC-3.12** Given the provider verifies a payment whose amount or currency differs from the order's, when the server processes the result, then the order is not marked paid, the order becomes failed, an audit event with both amounts is written, and the customer sees a failure message.
- **AC-3.13** Given the provider is unavailable or a provider call exceeds the 10-second timeout while I choose "Pay", then I see a retryable error, the order remains pending_payment with no confirmed provider session, my cart is unchanged, and on retry the same provider idempotency key (derived from the order id) is used so that at most 1 provider payment exists.

### US-4 See the payment outcome (REQ-6, REQ-4, REQ-23, REQ-24, REQ-9)

As a customer, I want a clear result after paying so that I know whether my order went through.

- **AC-4.1** Given my payment succeeded, when I return to the shop, then a confirmation page shows the order number, total and status within 5 seconds of the return, and no email is sent.
- **AC-4.2** Given my card was declined or the payment failed, when I return to the shop, then I see a failure message that does not expose provider internals, the order is failed (and remains in history with that status), I am not charged, my cart is intact, and choosing to pay again creates a new order.
- **AC-4.3** Given I cancel on the hosted payment page, when I return to the shop, then the order is not changed to cancelled by the browser return alone: the server cancels the provider session and confirms with the provider that no payment was taken, then marks the order cancelled (if the provider reports a payment, the order becomes paid instead); I am not charged, my cart is intact, and I can retry (a retry creates a new order) or leave.
- **AC-4.4** Given the provider has not yet reported a final result when I return, when the confirmation page loads, then it shows a "payment processing" state, and it shows the final state within 30 seconds of the provider's result; the server reconciles every pending order with the provider every 60 seconds, and if no result ever arrives the page keeps showing "payment processing" with a refresh action until the order is expired (AC-4.5).
- **AC-4.5** Given a pending order, when its provider payment session reaches its lifetime (25 minutes after order creation), then the provider session is closed at the provider; and when 30 minutes have elapsed since the order was created, then the server first cancels the provider session and verifies with the provider that no payment was taken, then marks the order "expired" (if the provider reports a payment, the order becomes paid instead), and the expired order is not shown in order history.
- **AC-4.6** Given my payment is verified as successful, when the order becomes paid, then for each line snapshotted in the order my cart quantity is reduced by the snapshotted quantity and the line is removed at zero, and lines or quantities added after "Pay" remain (for an unchanged cart this empties the cart); given the payment is not successful, then the cart is not changed.
- **AC-4.7** Given an order is expired, cancelled or failed, when a verified provider success with matching amount and currency arrives for it (late success), then the order becomes paid, an audit event "late_payment_recovered" is written with both timestamps, the order appears in order history as paid, and the cart is not changed. An integration test replays a success callback after the expiry job and checks this outcome.
- **AC-4.8** Given I request the confirmation or payment status of another customer's order or payment reference (by order id or reference in the URL), when the API processes it, then it returns HTTP 404 with a body identical to that for a non-existent reference, and an audit event is written.
- **AC-4.9** Given my session expired while I was on the hosted payment page, when I return to the shop, then I am directed to sign in and, after sign-in, I see the outcome page of my order (reached by a same-origin relative path, AC-13.7).

### US-5 View my order history (REQ-7, REQ-9)

As a customer, I want to see a list of my orders so that I can review what I bought.

- **AC-5.1** Given I am signed in and have orders, when I open order history, then I see only my own orders with status paid, pending_payment or failed (cancelled and expired orders are not listed), newest first, each with order number, date, status and total.
- **AC-5.2** Given I have more than 20 orders, when I open order history, then 20 are shown with a way to reach the next page, and every order appears exactly once across pages with none missed or repeated.
- **AC-5.3** Given I have no orders, when I open order history, then an empty state with a call to action to continue shopping is shown, not an error.
- **AC-5.4** Given I have just completed a payment, when I open order history, then the new order appears within 5 seconds of the confirmation.
- **AC-5.5** Given I am not signed in, when I request order history (UI or API), then the API returns HTTP 401 and no order data is returned.
- **AC-5.6** Given order history fails to load, when the error occurs, then an error message with a retry action is shown and no partial or stale data of another customer is displayed.
- **AC-5.7** Given two customers each have orders, when customer A requests history, then 0 of customer B's orders appear in any response (verified for list and pagination parameters).

### US-6 View order detail (REQ-8, REQ-9)

As a customer, I want to open one order so that I can see exactly what it contained and its status.

- **AC-6.1** Given I select one of my orders, when the detail loads, then it shows order number, date, status, payment status, each line (name, quantity, unit price, line total, as snapshotted at order creation) and the total.
- **AC-6.2** Given I request an order id that belongs to another customer, when the API processes it, then it returns HTTP 404 with a response body identical to that for a non-existent order, and an audit event is written.
- **AC-6.3** Given I request a non-existent or malformed order id, when the API processes it, then it returns HTTP 404 (non-existent) or 400 (malformed) using the standard error model.
- **AC-6.4** Given any order detail response, when its payload is inspected, then it contains no PAN, CVV or provider secret, and shows only card brand and last 4 digits if supplied by the provider, otherwise no payment card data.
- **AC-6.5** Given I am not signed in, when I request an order detail, then the API returns HTTP 401.

### US-7 Audit and privacy of order data (REQ-11, REQ-12, REQ-10)

As the product owner, I want an audit trail and privacy controls on order data so that payments are traceable and personal data is protected.

- **AC-7.1** Given any of: checkout started, order created, payment outcome received (success, failure, cancel), late payment recovered, callback rejected, ownership-check denial, registration, sign-in success, sign-in failure, sign-in throttled (a delay of 1 second or more applied), sign-out, when it occurs, then an audit event is recorded with timestamp (UTC), event type, actor id (or, for unauthenticated attempts, a keyed hash of the attempted email using HMAC with a secret supplied via the environment, never an unkeyed hash), order id where applicable, outcome and correlation id, and with no card data, passwords or secrets.
- **AC-7.2** Given the audit log and application logs, when sampled across a full end-to-end test run, then 0 entries contain PAN, CVV, passwords, session credentials, provider secret keys, or full customer personal data beyond identifiers.
- **AC-7.3** Given an order status change, when it is attempted, then only these transitions are accepted: pending_payment to paid, failed, cancelled or expired; and, only by a provider-verified late success with matching amount and currency (AC-4.7), expired, cancelled or failed to paid. paid is terminal; no other transition is accepted. Any rejected transition is audited.
- **AC-7.4** Given an order is paid, when any request attempts to change its total or line items, then the change is rejected.
- **AC-7.5** Given the data is synthetic, when the POC environment is torn down, then orders, carts, accounts and audit records are deleted with the environment and a record of the teardown (what, when, by whom) is kept outside the torn-down environment (for example in the GitHub deployment record; exact location fixed in Phase 4); no customer-initiated deletion is offered.

### US-8 Browse the catalogue (REQ-14, REQ-20)

As a shopper, I want to browse the products so that I can find something to buy.

- **AC-8.1** Given the catalogue contains products, when I open the catalogue, then I see products with name, price and optional image placeholder, 20 per page, and every product appears exactly once across pages.
- **AC-8.2** Given the catalogue contains no products, when I open it, then an empty state is shown, not an error.
- **AC-8.3** Given the catalogue fails to load, when the error occurs, then an error message with a retry action is shown.
- **AC-8.4** Given amounts of $0.50, $1,234.56 and $1,000,000.00 passed to the price display, when they are displayed anywhere in the UI, then each is shown in exactly that USD format (currency symbol, thousands separator, two decimals). This tests formatting only; it does not imply a catalogue price of that size is purchasable (see AC-1.7).
- **AC-8.5** Given I am not signed in, when I request the catalogue list (UI or API), then I can view it (HTTP 200) and no cart actions are available to me.
- **AC-8.6** Given the seed procedure is run twice on an empty database, when it completes, then the catalogue contains the same 100 products with no duplicates (products keyed by a stable id).

### US-9 View a product (REQ-15)

As a shopper, I want to see a product's details so that I can decide whether to buy it.

- **AC-9.1** Given a product exists, when I open it, then I see its name, description, price in USD and an "Add to cart" action (and the optional image placeholder).
- **AC-9.2** Given I request a product id that does not exist, when the page or API is called, then HTTP 404 and a "product not found" state with a link back to the catalogue are shown.
- **AC-9.3** Given I am not signed in, when I choose "Add to cart", then no cart change occurs and I am directed to sign in, after which I return to the product, reached only by a same-origin relative path (AC-13.7).

### US-10 Add a product to my cart (REQ-16, REQ-9)

As a customer, I want to add products to my cart so that I can buy several things at once.

- **AC-10.1** Given I am signed in, when I add product P with quantity 2, then my cart contains one line for P with quantity 2 and the cart count shown to me is updated.
- **AC-10.2** Given my cart already has a line for P, when I add P again, then the existing line's quantity is increased and no second line for P is created.
- **AC-10.3** Given a line's quantity would exceed 10, or I submit a quantity of 0, a negative number or a non-integer, when the request is processed, then it is rejected (HTTP 400) with a message stating the allowed range and the cart is unchanged.
- **AC-10.4** Given I add a product id that does not exist, when the request is processed, then HTTP 404 is returned and the cart is unchanged.
- **AC-10.5** Given I am not signed in, when I call the add-to-cart API, then HTTP 401 is returned and nothing is stored.
- **AC-10.6** Given the request contains properties not in the contract (for example a client-supplied price), when it is processed, then it is rejected with HTTP 400 and the cart is unchanged.
- **AC-10.7** Given my cart already has 50 distinct lines, when I add a 51st distinct product, then the request is rejected (HTTP 409) with a message stating the 50-line maximum and the cart is unchanged; adding more of a product already in the cart is still allowed within the quantity limit.
- **AC-10.8** Given my cart has 49 distinct lines, when I add a 50th distinct product, then it is accepted and the cart has 50 lines.

### US-11 Manage and view my cart (REQ-16, REQ-9)

As a customer, I want to view and change my cart so that it contains exactly what I want to buy.

- **AC-11.1** Given my cart has lines, when I open the cart, then each line shows product name, quantity, unit price and line total, and the cart total equals the sum of line totals in USD format; the unit price shown is the price last shown to me for that line and is refreshed to the current catalogue price when a checkout mismatch is reported (AC-1.4).
- **AC-11.2** Given a cart line, when I change its quantity to a valid value (1 to 10), then the line total and cart total update and the new quantity persists after reload.
- **AC-11.3** Given a cart line, when I change its quantity to an invalid value (0, negative, non-integer, above 10), then the change is rejected with a message stating the allowed range and the quantity is unchanged.
- **AC-11.4** Given a cart line, when I remove it, then it disappears, the totals update, and it stays removed after reload.
- **AC-11.5** Given my cart is empty, when I open it, then an empty state with a link to the catalogue is shown and the checkout action is unavailable.
- **AC-11.6** Given I have a cart with lines, when I sign out and sign in again (or sign in from a second browser), then the cart contents are identical to before.
- **AC-11.7** Given a cart line id that belongs to another customer, when I try to read, change or remove it via the API, then HTTP 404 is returned, nothing changes, and 0 of the other customer's cart data appears in the response.
- **AC-11.8** Given the cart fails to load, when the error occurs, then an error message with a retry action is shown and no other customer's data is displayed.

### US-12 Register an account (REQ-17, REQ-19)

As a visitor, I want to register with my email and a password so that I can shop and see my orders.

- **AC-12.1** Given I provide a valid email and a password meeting the policy (12 to 128 characters, not on a common-password list), when I submit registration, then an account is created, I am signed in automatically, and no password or hash appears in the response.
- **AC-12.2** Given an email that is not a valid address format, when I submit, then the field shows a validation message and no account is created (API: HTTP 400).
- **AC-12.3** Given a password that does not meet the policy (fewer than 12 or more than 128 characters, or on a common-password list; no composition rules), when I submit, then the password field states the rule that failed and no account is created.
- **AC-12.4** Given an account exists for an email, when someone registers with the same email in any letter case (email trimmed, compared case-insensitively, maximum 254 characters), then no second account is created and the response is HTTP 409 with a message that the email is already registered.
- **AC-12.5** Given an account was created, when the database is inspected, then the stored credential is a salted, adaptive one-way hash and 0 plaintext or reversibly encrypted passwords exist (NFR-13).
- **AC-12.6** Given the registration request contains properties not in the contract, when it is processed, then it is rejected with HTTP 400 and no account is created.
- **AC-12.7** Given registration succeeded, when the audit log is read, then a registration event exists without the password (AC-7.1).
- **AC-12.8** Given I hold a pre-registration session credential, when registration succeeds, then a new session credential is issued, and replaying the earlier credential returns HTTP 401.
- **AC-12.9** Given 20 concurrent registration requests for the same email in different letter cases, when they are processed, then exactly 1 account exists (a case-insensitive unique constraint on email enforces this in the database) and the others receive HTTP 409.
- **AC-12.10** Given password length is measured in Unicode code points after NFC normalisation, when a 128-code-point password containing multi-byte characters is registered, then it is accepted and the full input is used for hashing; and given two passwords that share their first 72 bytes but differ afterwards, when each is registered then used to sign in, then only the matching password verifies (no truncation).

### US-13 Sign in (REQ-18, REQ-19)

As a registered customer, I want to sign in so that I can use my cart and see my orders.

Progressive delay schedule (OQ-35): let f be the number of failed sign-in attempts for the same email (normalised as in AC-12.4, whether or not an account exists) within the sliding 15-minute window before the current attempt. The server delays its response to the current attempt by: f = 0 to 2: 0 seconds; f = 3: 1 second; f = 4: 2 seconds; f = 5: 4 seconds; f = 6: 8 seconds; f >= 7: 16 seconds (cap). The delay applies to every attempt for that email, including one with the correct password.

- **AC-13.1** Given a registered account, when I submit the correct email and password, then I am signed in, a session is established per NFR-14, and I am taken to the page I originally requested (or the catalogue).
- **AC-13.2** Given a wrong password for an existing email, or an email with no account, when I submit, then the HTTP status, response body and visible message are identical in both cases ("Email or password is incorrect") and reveal nothing about whether the account exists (NFR-16).
- **AC-13.3** Given f failed attempts for an email in the window (existing account or not), when I make the next attempt, then the response is delayed per the schedule above, never returns an HTTP 429 because of the per-email count, and a correct password still signs me in after the delay (no lockout: for example at f = 7 a correct sign-in returns HTTP 200 after about 16 seconds); an audit event "sign-in throttled" is written for every delayed attempt (delay 1 second or more).
- **AC-13.4** Given my session has expired (30 minutes idle or 8 hours absolute), when I make an authenticated request, then HTTP 401 is returned and the UI directs me to sign in and returns me to my previous page afterwards (same-origin relative path only, AC-13.7).
- **AC-13.5** Given a sign-in succeeds or fails, when the audit log is read, then an event with outcome exists and contains no password.
- **AC-13.6** Given the sign-in service is unavailable, when I submit, then a generic error with a retry action is shown and no session is created.
- **AC-13.7** Given a sign-in return target taken from the request, when it is anything other than a same-origin relative path (for example `https://evil.example`, `//evil.example`, `javascript:alert(1)`), then it is ignored and I land on the catalogue; a same-origin relative path such as `/cart` is honoured.
- **AC-13.8** Given I hold a pre-authentication session credential, when sign-in succeeds, then a new session credential is issued and replaying the earlier credential returns HTTP 401.
- **AC-13.9** Given 8 consecutive wrong-password attempts against an unknown email and against an existing email, when the responses are compared attempt by attempt, then status, body and headers (excluding Date and correlation id) are identical, and the response delay follows the same schedule, with a median difference of 50 ms or less between the two cases at each attempt number.
- **AC-13.10** Given f failed attempts below the point of a successful sign-in, when a correct sign-in succeeds, then the failure count for that email resets to zero and the next attempt has no delay; and given no failed attempt for 15 minutes, when the next attempt is made, then there is no delay (failures age out of the sliding window).

### US-14 Sign out (REQ-18)

As a signed-in customer, I want to sign out so that nobody else can use my account on this device.

- **AC-14.1** Given I am signed in, when I choose "Sign out", then my session is invalidated on the server, and replaying the previous session credential returns HTTP 401.
- **AC-14.2** Given I have signed out, when I use the browser's back button or open a protected page, then no cart, order or account data is shown and I am directed to sign in.
- **AC-14.3** Given my session has already expired, when I choose "Sign out", then I am shown the signed-out state without an error.

### US-15 Paid order data stays unchanged (REQ-21, REQ-22, REQ-20, REQ-8)

As the product owner, I want order records to keep exactly what the customer bought and paid so that re-seeding or product changes never alter history.

- **AC-15.1** Given an order is created, when its lines are stored, then each line holds product id, product name and unit price in integer cents copied at creation, and order detail reads these stored values, not live product data.
- **AC-15.2** Given a paid order exists, when the seed procedure is re-run against that non-empty database with a changed price and name for a product in the order, then the order detail response is unchanged byte for byte, the sum of line totals still equals the order total, and no order line is lost.
- **AC-15.3** Given a product is referenced by one or more orders, when it is removed from the seed set or the seed procedure runs, then the product is not hard-deleted (it is flagged not purchasable, hidden from new carts and checkout) and the seed procedure does not fail.
- **AC-15.4** Given any API response or provider request that contains an amount, when its schema is inspected, then the amount is an integer number of cents with an explicit currency, and no floating-point money value appears (contract test).

## 9. Out of scope

- Real card payments, real customer traffic, real personal data (charter).
- Multi-tenant or multi-region deployment (charter).
- Storing cards or card data, saved cards, wallets (other than hosted-page methods the provider offers by default) and non-card payment methods; direct-post or provider JavaScript fields rendered in our own page elements (excluded by REQ-3).
- Refunds, returns, cancellations after payment, partial payments, invoices, subscription billing. A late success on an expired order makes the order paid (AC-4.7); it is not refunded.
- Admin or support tooling for viewing other customers' orders.
- Guest checkout (decided: not allowed) and guest carts.
- Social login, multi-factor authentication, password reset or recovery, email verification (all explicitly out of scope per the Product Owner).
- Account profile editing, account deletion, change of email or password, remember-me, session management screens, account lockout.
- Admin UI for products or catalogue management (products are seeded; OQ-26 decided).
- Product search, filtering, sorting, categories, reviews and wishlists (the catalogue is list and view only).
- Order search, filtering and export (history is a paginated list only).
- Shipping, fulfilment and tracking; tax, discounts and promo codes; delivery address; inventory tracking and reservation.
- Confirmation or any other email.
- Non-USD currencies, languages other than English.
