## 1. Problem statement

The Shop Platform has no way for a customer to find products, build a cart, turn it into a paid order, or see what they previously bought. Without checkout the platform earns nothing; without order history customers cannot confirm or review purchases. This feature lets a customer register and sign in, browse a basic product catalogue, keep a cart, check out and pay by card through a payment provider's hosted page (test mode only, so card data never reaches our servers), and view their own order history and order details.

Because the repository is greenfield, no catalogue, cart, customer account or authentication capability exists. The Product Owner has decided that this feature delivers a minimal version of each (OQ-1, OQ-2).

## 3. Scope statement

- **In scope:**
  - Basic product catalogue: browse/list and view products; products are seeded, no admin UI.
  - Cart: add, remove, change quantity, view; persisted per customer and kept across sign-out/sign-in.
  - Basic customer accounts: register, sign in, sign out with email and password.
  - Checkout from the cart, order summary, hosted card payment (test mode), payment outcome handling (including late, failed and unknown outcomes), order confirmation.
  - Order history list and order detail.
  - Audit logging, operator alerts for payment anomalies, and privacy and retention rules for order and account data.
- **UI in scope: YES.** The customer-facing web app (React) is in scope for catalogue, product, cart, registration, sign-in, checkout, confirmation, history and detail screens, so Phase 3 (UX spec, prototype, HG-2) applies.
- Out of scope: see section 9.

## 5. User stories and acceptance criteria

All ACs are Given/When/Then. Time targets are server-side or end-to-end as stated, measured in the CI/staging test environment. Money is USD displayed as `$1,234.56`.

### US-1 Start checkout (REQ-1, REQ-2, REQ-13, REQ-9, REQ-22, REQ-23)

As a customer, I want to start checkout from my cart so that I can pay for the items.

- **AC-1.1** Given I am signed in and my cart has at least one item, when I choose "Checkout", then I am shown the order summary, the Checkout action itself creates no order and starts no payment, and no order is marked paid; if an active pending order already exists for this unchanged cart, it is left as it is and not duplicated.
- **AC-1.2** Given I am signed in and my cart is empty, when I attempt to check out (via UI or API), then checkout is refused with a message stating the cart is empty (API: HTTP 4xx with the error model), and no order record is created.
- **AC-1.3** Given I am not signed in, when I attempt to start checkout (UI or API), then the API returns HTTP 401, no order is created, and the UI directs me to sign in; after I sign in, my cart is intact (see AC-11.6).
- **AC-1.4** Given my cart contains a line that is no longer purchasable (product flagged not purchasable) or whose price differs from the current catalogue price, when I start checkout, then no order is created and no payment is started, the message lists each affected item and the change, price-changed lines in the cart are updated to the current price (which increments the cart version), not-purchasable lines are flagged and must be removed by me, and I can return to the cart.
- **AC-1.5** Given I send a checkout request referencing a cart owned by another customer, when the API processes it, then it returns HTTP 404 and creates nothing.
- **AC-1.6** Given a checkout was rejected under AC-1.4 for price changes only, when I start checkout again without changing the cart, then the summary is shown at the new price and I can proceed to pay.
- **AC-1.7** Given a cart total of $0.49, $0.50, $999,999.99 and $1,000,000.00 (one cent below the minimum, the minimum, the maximum, one cent above the maximum), when I start checkout, then $0.50 and $999,999.99 proceed, and $0.49 and $1,000,000.00 are blocked with a message stating the allowed range, and no order is created.

### US-2 Review order summary (REQ-2, REQ-22)

As a customer, I want to see exactly what I will pay so that I can confirm before paying.

- **AC-2.1** Given I am at checkout, when the summary loads, then it lists every cart line with name, quantity, unit price and line total, plus the order total, all formatted as USD (`$1,234.56`).
- **AC-2.2** Given a summary is displayed, when I compare amounts, then the order total equals the sum of line totals (no tax, shipping or discounts), computed in integer cents, with zero rounding discrepancy in 100% of the automated test cases.
- **AC-2.3** Given a checkout, summary or pay request that contains price, amount or total fields, when the API processes it, then it is rejected with HTTP 400 (the same behaviour as any unknown field, AC-10.6) and creates no order; the server never reads amounts from the client, and the stored order always uses server-side prices (verified by an API test comparing the stored total to catalogue prices for a normal request).
- **AC-2.4** Given the summary cannot be loaded (server error), when the failure occurs, then an error message with a retry action is shown and the cart is unchanged.

### US-3 Pay by card via hosted payment (REQ-3, REQ-4, REQ-5, REQ-9, REQ-11, REQ-22, REQ-23, REQ-24, REQ-25)

As a customer, I want to pay by card on a secure page so that my card details stay protected.

- **AC-3.1** Given I confirm the summary, when I choose "Pay", then exactly one pending_payment order is created with its lines snapshotted from the cart (or the existing active order is reused under AC-3.8), I am taken by full redirect to the provider's hosted payment page (or shown provider-hosted iframe fields), and the amount shown there equals the order total.
- **AC-3.2** Given I complete a payment in a recorded end-to-end run, when the HTTP traffic to our API and the application logs and database are inspected, then there are 0 occurrences of a PAN, CVV or expiry value, and no card input fields are rendered by our own page elements outside provider-hosted content.
- **AC-3.3** Given the application is configured with a non-test (live) provider credential, when the API starts, then it refuses to start and logs a configuration error without printing the credential. How a live credential is recognised (for example key prefix or provider mode flag) depends on the provider and is defined in Phase 4.
- **AC-3.4** Given I click "Pay" twice within 1 second, or refresh or navigate back and resubmit with an unchanged cart, when the requests are processed, then exactly 1 order and exactly 1 provider payment exist (the second request reuses the active order, REQ-23).
- **AC-3.5** Given the provider reports a successful payment, when the server verifies it with the provider, then the order status becomes "paid" and the paid amount equals the order total.
- **AC-3.6** Given the provider's confirmation callback is delivered more than once, when each delivery is processed, then the order is updated once and later deliveries return success without changing the order.
- **AC-3.7** Given a callback or return request that fails authenticity verification (invalid signature or unknown reference), when it is received, then it is rejected with HTTP 4xx, the order is unchanged, and an audit event is written. The callback endpoint is the only endpoint not requiring a customer session (REQ-9).
- **AC-3.8** Given I have the same unchanged cart (same cart version) open in two tabs, when I choose "Pay" in both while the provider session is open with at least 5 minutes remaining, then exactly 1 pending order and exactly 1 provider payment exist and both tabs lead to the same payment session.
- **AC-3.9** Given I have a pending order, when I go back, change the cart (add, remove or change a line) and choose "Checkout" then "Pay", then the old order is cancelled after the provider confirms its session is closed (or, if the provider reports it already paid, the old order becomes paid and the new checkout is refused with a message), a new order with the new lines is created, exactly 1 pending order exists, and at most 1 successful charge results.
- **AC-3.10** Given I edit my cart while my order is pending payment, when the original payment is then verified as successful, then the paid order contains the original snapshotted lines and total, and the cart changes made after "Pay" remain in my cart (see AC-4.6).
- **AC-3.11** Given two browser sessions of mine start checkout at the same moment with different cart versions, when both choose "Pay", then exactly 1 pending order remains active (the later supersedes the earlier under AC-3.9) and at most 1 successful charge results.
- **AC-3.12** Given the provider verifies a payment whose amount or currency differs from the order's, when the server processes the result, then the order is not marked paid, the order becomes failed, an audit event with both amounts is written, an operator alert is raised within 5 minutes (NFR-22), and the customer sees a failure message that tells them the payment could not be completed, that if they were charged they should contact support quoting the order number, and that the shop will review it.
- **AC-3.13** Given the provider is unavailable or a provider call exceeds the 10-second timeout while I choose "Pay", then I see a retryable error, the order remains pending_payment with no confirmed provider session, my cart is unchanged, and on retry, while at least 5 minutes of the 25-minute session lifetime remain, the same order and the same provider idempotency key (derived from the order id) are used so that at most 1 provider payment exists; otherwise AC-3.17 applies.
- **AC-3.14** Given my previous order failed (or was cancelled or expired) and my cart is unchanged, when I choose "Pay" again (including a double click), then exactly 1 new order is created with a new provider idempotency key, exactly 1 new provider payment exists, the previous terminal order is unchanged, and no duplicate payment exists at the provider.
- **AC-3.15** Given I have an active pending order for an unchanged cart that has no open provider session (the session closed, or none was ever confirmed) or whose session has less than 5 minutes of lifetime remaining (for example at minute 27), when I choose "Pay", then the old order is cancelled (status "cancelled", hidden from order history) after the provider confirms no payment was taken (if the provider reports a payment, the old order becomes paid and no new order is created), a new order with a payable session is created, and no more than 1 order is pending at any time.
- **AC-3.16** Given the provider is unavailable when a superseding checkout needs to cancel my old pending order (AC-3.9, AC-3.15), when I choose "Pay", then the old order stays pending_payment, no new order is created, I see a retryable message that my previous payment is still being confirmed, and a new checkout is blocked until the old order can be closed.
- **AC-3.17** Given a provider call timed out at "Pay" so my order has no confirmed provider session (AC-3.13), when I retry at minute 26 (or at any time after minute 20, when fewer than 5 minutes of session lifetime remain), then AC-3.15 applies: the old order is cancelled after the provider confirms no payment exists for it, exactly 1 new order is created, exactly 1 new provider payment exists (new idempotency key) with a session that expires at the new order's creation plus 25 minutes, and no more than 1 order is pending.
- **AC-3.18** Given I have a pending order for an unchanged cart with an open provider session, when I choose "Pay" at minute 24 (1 minute remaining, below the 5-minute minimum), then the old order is cancelled after the provider confirms no payment was taken (or becomes paid if the provider reports a payment, and no new order is created), exactly 1 new order with a full-lifetime session is created, and no more than 1 order is pending; and when I choose "Pay" at minute 20 (exactly 5 minutes remaining), then the existing order and session are reused and no new order is created.

### US-4 See the payment outcome (REQ-6, REQ-4, REQ-9, REQ-10, REQ-11, REQ-23, REQ-24, REQ-25)

As a customer, I want a clear result after paying so that I know whether my order went through.

- **AC-4.1** Given my payment succeeded, when I return to the shop, then a confirmation page shows the order number, total and status within 5 seconds of the return, and no email is sent.
- **AC-4.2** Given my card was declined or the payment failed, when I return to the shop, then I see a failure message that does not expose provider internals, the order is failed (and remains in history with that status), I am not charged (unless a later verified success arrives, AC-4.7), my cart is intact, and choosing to pay again creates a new order (AC-3.14).
- **AC-4.3** Given I cancel on the hosted payment page, when I return to the shop, then the order is not changed to cancelled by the browser return alone: the server cancels the provider session and confirms with the provider that no payment was taken, then marks the order cancelled (if the provider reports a payment, the order becomes paid instead); I am not charged, my cart is intact, and I can retry (a retry creates a new order) or leave.

A late success (AC-4.7) is excluded from this rule.

An integration test replays a success callback after the expiry job and checks this outcome.

- **AC-4.11** Given order A for my cart expired, order B for the same lines (same cart version) is paid, and then a verified late success arrives for order A, when the server processes it, then order A becomes paid, both orders are flagged `duplicate_payment_review`, an operator alert is raised within 5 minutes, the cart is unchanged, and no automatic refund is made; the operator resolves it outside the system.

### US-13 Sign in (REQ-18, REQ-19, REQ-11, REQ-25)

As a registered customer, I want to sign in so that I can use my cart and see my orders.

Progressive delay with a single per-email slot (approach decided in OQ-35; numbers and concurrency design in OQ-40; per-email slot of 1 in OQ-46). For each normalised email (as in AC-12.4, whether or not an account exists) the server keeps a failure count f for the sliding 15-minute window. f is increased **when an attempt arrives** (an attempt still in progress counts as a failure until it succeeds) and a successful sign-in resets it to zero. The delay for an attempt is set by the f value it saw on arrival: f = 0 to 2: 0 seconds; f = 3: 1 second; f = 4: 2 seconds; f = 5: 4 seconds; f = 6: 8 seconds; f >= 7: 16 seconds (cap). The delay is enforced **before** the password is checked. **At most one attempt per email may be waiting or being checked at a time (the per-email slot, cap 1).** Any other attempt for that email that arrives while the slot is taken is answered with the same generic failure after its own scheduled delay, **without checking the password**, identical for existing and unknown emails. The slot is free again only when the holder's check has ended, so successive password checks for one email are at least delay(f) apart. For an unknown email the server performs equivalent hashing work so timing matches.

- **AC-13.1** Given a registered account, when I submit the correct email and password, then I am signed in, a session is established per NFR-14, and I am taken to the page I originally requested (or the catalogue).
- **AC-13.2** Given a wrong password for an existing email, or an email with no account, when I submit, then the HTTP status, response body and visible message are identical in both cases ("Email or password is incorrect") and reveal nothing about whether the account exists (NFR-16).
- **AC-13.3** Given f failed attempts for an email in the window (existing account or not), when I make the next attempt, then the response is delayed per the schedule above before any password check, never returns an HTTP 429 because of the per-email failure count, and a correct password that holds the slot still signs me in after the delay (no lockout: for example at f = 7 a correct sign-in returns HTTP 200 after about 16 seconds when no other attempt for that email is waiting or being checked); an audit event "sign-in throttled" is written for every delayed attempt (delay 1 second or more).
- **AC-13.4** Given my session has expired (30 minutes idle or 8 hours absolute), when I make an authenticated request, then HTTP 401 is returned and the UI directs me to sign in and returns me to my previous page afterwards (same-origin relative path only, AC-13.7).
- **AC-13.5** Given a sign-in succeeds or fails, when the audit log is read, then an event with outcome exists and contains no password.
- **AC-13.6** Given the sign-in service is unavailable, when I submit, then a generic error with a retry action is shown and no session is created.
- **AC-13.7** Given a sign-in return target taken from the request, when it does not satisfy the rule, then it is ignored and I land on the catalogue. The rule: after URL-decoding once and parsing against our origin the resolved origin equals our origin, and the raw value starts with a single "/" followed by neither "/" nor "\" and contains no tab, newline or other control characters. The redirect uses the path, query and fragment of the parsed, validated URL, never the raw input, and no further decoding happens after validation. Negative examples that each land on the catalogue: `https://evil.example`, `//evil.example`, `javascript:alert(1)`, `/\evil.example`, `/%2F%2Fevil.example`, `/%5Cevil.example`, `/%09/evil.example`, `/\t/evil.example`, `/%252F%252Fevil.example`. A same-origin relative path such as `/cart` is honoured.
- **AC-13.8** Given I hold a pre-authentication session credential, when sign-in succeeds, then a new session credential is issued and replaying the earlier credential returns HTTP 401.
- **AC-13.9** Given 8 consecutive wrong-password attempts against an unknown email and against an existing email, when the responses are compared attempt by attempt, then status, body and headers (excluding Date and correlation id) are identical, and the response delay follows the same schedule, with a median difference of 50 ms or less between the two cases at each attempt number.
- **AC-13.10** Given f failed attempts below the point of a successful sign-in, when a correct sign-in succeeds, then the failure count for that email resets to zero and the next attempt has no delay; and given no failed attempt for 15 minutes, when the next attempt is made, then there is no delay (failures age out of the sliding window).
- **AC-13.11** Given 20 wrong-password attempts for one email sent at the same moment from 4 source IPs (5 each, within the per-IP limits and the per-IP held cap), when they are processed, then exactly 1 password check occurs (the attempt that holds the per-email slot); the other 19 attempts are answered with the generic failure after their scheduled delay without a password check; none returns HTTP 429; the responses are identical for an existing email and for an unknown email; and a correct password among the 19 is not checked.
- **AC-13.12** Given sign-in responses are being held for delay (including the generic delayed failures of AC-13.11), when more than 5 are held for one source IP, or more than 200 across the service, then each further attempt is answered immediately with HTTP 429 and `Retry-After: 16`, with an identical body regardless of the email or whether an account exists, is not counted as a failed attempt and does not reach a password check. Every cap event is audited ("sign-in response cap reached"); the per-IP cap is audited only, and the service-wide cap raises one aggregated alert per 15 minutes with a count (AC-7.6).
- **AC-13.13** Given attempts for one email are sent every 3 seconds for 5 minutes from 15 source IPs (about 7 attempts each, within the per-IP limits), when they are processed, then no more password checks occur than the sequential schedule allows in the same elapsed time, that is at most 7 + floor((300 - 15) / 16) = 24 checks in the 300 seconds (not 5 checks per 16 seconds), and the responses are identical for an existing email and for an unknown email.

## 9. Out of scope

- Real card payments, real customer traffic, real personal data (charter).
- Multi-tenant or multi-region deployment (charter).
- Storing cards or card data, saved cards, wallets (other than hosted-page methods the provider offers by default) and non-card payment methods; direct-post or provider JavaScript fields rendered in our own page elements (excluded by REQ-3).
- Refunds, returns, cancellations after payment, partial payments, invoices, subscription billing. A late success on an expired order makes the order paid (AC-4.7) and a duplicate payment is flagged for the operator (AC-4.11); neither is refunded by the system.
- Admin or support tooling for viewing other customers' orders.
- Guest checkout (decided: not allowed) and guest carts.
- Social login, multi-factor authentication, password reset or recovery, email verification (all explicitly out of scope per the Product Owner).
- Account profile editing, account deletion, change of email or password, remember-me, session management screens, account lockout.
- Admin UI for products or catalogue management (products are seeded; OQ-26 decided).
- Product search, filtering, sorting, categories, reviews and wishlists (the catalogue is list and view only).
- Order search, filtering and export (history is a paginated list only).
- Shipping, fulfilment and tracking; tax, discounts and promo codes; delivery address; inventory tracking and reservation.
- Confirmation or any other email to customers.
- Non-USD currencies, languages other than English.
